2. LightningDataModule의 setup 메서드와 train_dataloader 메서드의 역할 차이를 설명할 수 있으신가요? 왜 데이터 분할과 DataLoader 생성을 분리하는 것이 중요한가요?
- 역할 차이: setup 메서드는 데이터를 다운로드하고, 전처리(transform)를 설정하며, 전체 데이터를 Train/Val/Test 셋으로 분할하여 데이터셋(Dataset) 객체를 준비하는 역할을 합니다. 반면 train_dataloader는 setup에서 준비된 훈련 데이터셋을 활용해 모델에 배치를 공급할 DataLoader 객체를 생성해 반환합니다.

- 분리 이유: 동일한 데이터 처리 로직을 여러 모델에서 쉽게 재사용하기 위함입니다. 또한 분산 학습 환경에서 setup을 통해 각 GPU 프로세스에 맞게 데이터 분할이 자동으로 안전하게 처리되고, num_workers나 batch_size 같은 설정을 한 곳에서 통합 관리할 수 있기 때문입니다.


3. 이 장에서 배운 _shared_step 패턴을 자신의 프로젝트에 적용한다면, 공통 로직과 각 단계(학습/검증/테스트)에서 달라지는 부분은 각각 무엇인가요?
- 공통 로직: 입력 데이터와 정답 레이블을 분리하고, 모델에 순전파를 수행하여 예측값(logits)을 얻은 뒤, 손실 함수와 예측 결과를 통해 loss와 accuracy 같은 공통 평가 지표를 계산하는 핵심 연산 과정입니다.

- 달라지는 부분: 반환된 지표를 바탕으로 로깅하는 방식이 다릅니다. training_step에서는 모델 업데이트를 위해 최종 계산된 loss를 반드시 반환해야 하며, 주로 스텝 단위 로깅(on_step=True)을 수행합니다. 반면 validation_step과 test_step에서는 각각의 단계에 맞는 이름(val_loss, test_loss)으로 에포크 단위 집계(on_epoch=True) 및 프로그레스 바 표시 등의 로깅을 수행합니다.


4.  overfit_batches=1 테스트가 실패했을 때 의심해야 할 원인 3가지와, 각각의 디버깅 방법을 설명할 수 있으신가요?
- 그래디언트 계산 오류: 연산 그래프가 끊겨서 모델 가중치가 업데이트되지 않는 상황입니다. 각 레이어의 그래디언트(grad) 값을 출력하여 0이거나 None인 부분이 있는지 점검합니다.

- 데이터 셔플링 오류: 데이터와 레이블의 짝이 어긋나 순서가 뒤섞인 상황입니다. 모델에 들어가기 직전의 DataLoader 출력을 시각화(이미지와 라벨 출력)하여 정답이 제대로 매핑되었는지 육안으로 확인합니다.

- 수치적 불안정성: 연산 중 NaN(Not a Number)이나 Inf가 발생하는 상황입니다. 입력 데이터에 결측치가 있는지 점검하고, 학습률(Learning Rate)을 대폭 줄여보거나 혼합 정밀도 적용 전후의 상태를 비교합니다.


5. 8.13의 전체 코드를 여러분의 실제 프로젝트에 맞게 수정한다면, LitClassifier.__init__과 MyDataModule.setup에서 각각 무엇을 바꿔야 하는지 구체적으로 떠올려 보세요.

✅ Chapter 9 체크포인트

1. GPU 선택의 3대 지표(메모리 대역폭, 연산 속도, 인터커넥트) 중 분산 학습에서 가장 중요한 것은 무엇이며, 그 이유를 "고속도로와 톨게이트" 비유로 설명할 수 있으신가요?
- 분산 학습에서 가장 중요한 지표: 인터커넥트(Interconnect)입니다. 분산 학습 시 여러 GPU가 그래디언트를 서로 교환해야 하므로, GPU 간 직접적인 초고속 통신 속도가 전체 학습 속도를 결정하기 때문입니다.

- 고속도로와 톨게이트 비유: 본문에서 이 비유는 메모리 대역폭(Memory Bandwidth)을 설명할 때 사용되었습니다. GPU의 연산 속도(고속도로)가 아무리 빨라도, 메모리에서 연산 장치로 데이터를 가져오는 대역폭(톨게이트)이 좁으면 병목 현상이 발생하여 연산 장치가 유휴 상태로 대기하게 됩니다.



2. "시간당 비용"이 아니라 "실험당 비용"으로 GPU를 평가해야 하는 이유를 표의 숫자 예시를 활용하여 설명할 수 있으신가요?
: 클라우드에서 단순히 '시간당 대여료'가 가장 저렴한 머신을 고르면 처리 속도가 느려 전체 학습 시간이 길어집니다. 성능이 뛰어난 GPU의 시간당 비용이 더 비싸더라도, 압도적인 연산 속도로 학습 자체를 빠르게 끝낼 수 있어 결과적으로 "1회 실험에 들어가는 총비용"은 훨씬 저렴해집니다. 또한, 엔지니어의 대기 시간도 줄어들어 프로젝트 전체의 생산성을 높일 수 있습니다.


3. 스팟 인스턴스를 안전하게 사용하기 위해 반드시 갖춰야 할 전제 조건은 무엇인가요?
: 스팟 인스턴스는 클라우드 내 수요가 높아지면 언제든 인스턴스가 강제로 회수될 수 있습니다. 따라서 인스턴스가 종료되더라도 기존 학습 진행 상황을 잃지 않고 이어서 학습할 수 있도록 체크포인팅(Checkpointing) 자동화 기능이 반드시 갖춰져야 합니다.


4. 여러분이 실습에서 진행한 실험 중, W&B가 있었다면 어떤 점이 편리했을지 구체적으로 떠올려 보실 수 있나요?
: DLthon 해커톤에서 RAG 기반 4컷 만화 파이프라인을 개발하거나 ResNet 등을 활용한 컴퓨터 비전 모델을 학습시킬 때, W&B가 있었다면 여러 하이퍼파라미터를 변경하며 시도한 수십 번의 실험 결과를 대시보드에서 한눈에 비교할 수 있었을 것입니다. 주피터 노트북 등에 수동으로 기록할 필요 없이 학습률과 성능 간의 상관관계를 즉시 시각적으로 분석하고, GPU 및 메모리 사용량 같은 시스템 메트릭도 자동 수집되어 모델 최적화와 리소스 관리가 훨씬 수월했을 것입니다.



✅ Chapter 10 체크포인트

1. 스토리지 계층 구조의 지연 시간 차이가 DataLoader의 num_workers 설정에 어떤 영향을 미치는지 설명할 수 있으신가요?
: 디스크(스토리지)에서 데이터를 읽어오는 속도는 GPU 연산 속도에 비해 천문학적으로 느립니다. 이 지연 시간 차이로 인한 병목 현상을 극복하기 위해 num_workers를 늘려 여러 개의 프로세스가 다음 배치의 데이터를 디스크에서 메모리로 미리 읽어오게(Prefetch) 합니다. 이를 통해 GPU가 연산을 마친 뒤 다음 데이터를 기다리며 유휴 상태(대기 상태)에 빠지는 것을 방지할 수 있습니다.


2. "이진 데이터는 S3에, URL만 DB에"라는 원칙의 이유를 설명할 수 있으신가요? 이 원칙을 어겼을 때 어떤 문제가 발생하나요?
- 이유: 용량이 큰 이진 파일(이미지, 오디오, 비디오 등)은 무한 확장이 가능한 객체 저장소에 분리 보관하고, DB는 빠르고 가벼운 텍스트(URL) 처리만 담당하게 하여 시스템의 효율을 높이기 위함입니다.

- 발생 문제: 이 원칙을 어기고 데이터베이스에 이진 데이터를 직접 저장하면 DB의 전체 성능이 급격하게 저하되며, 데이터 백업 및 복제 작업도 매우 까다로워집니다.


3. OLTP와 OLAP의 차이를 "행 지향 vs 열 지향"의 관점에서, 각각 어떤 쿼리에 적합한지 예시와 함께 설명할 수 있으신가요?
- OLTP (행 지향 DB): 하나의 온전한 데이터(행 단위 레코드)를 빠르게 읽고 쓰는 데 최적화되어 있습니다. "사용자 A의 모든 주문 내역을 조회하라"와 같이 개별 트랜잭션을 즉각적으로 처리하는 쿼리에 적합합니다.

- OLAP (열 지향 DB): 특정 열(Column) 단위로만 데이터를 저장하고 읽어오므로 분석 속도가 매우 빠르고 데이터 압축률도 높습니다. "지난 30일간 전체 이미지의 평균 해상도를 계산하라"와 같이 대량의 데이터를 집계하고 통계를 분석하는 쿼리에 적합합니다.



✅ Chapter 11 체크포인트

1. 레이블링을 최소화하는 4가지 전략(자기주도 학습, 증강, 합성 데이터, 사용자 피드백)을 각각 한 문장으로 요약하고, 자신의 프로젝트에 적용 가능한 것을 골라보실 수 있나요?
- 자기주도 학습: 별도의 레이블 없이 데이터 자체의 구조(예: 마스킹 복원, 다음 토큰 예측)를 활용하여 모델을 학습시킵니다.

- 데이터 증강: 데이터의 본질적 의미는 유지하면서 표면적 특성(회전, 번역, 노이즈 추가 등)만 변형해 학습 데이터를 다량으로 만들어냅니다.

- 합성 데이터: 알고리즘이나 생성 모델(LLM 등)을 통해 이미 정답이 부여된 데이터를 직접 생성합니다.

- 사용자 피드백: 서비스 내에서 발생하는 사용자의 행동(클릭, 스킵, 좋아요 등)을 수집하여 암묵적인 레이블로 활용합니다.

- 프로젝트 적용 예시: RAG 기반 4컷 만화 생성 파이프라인의 경우, 만화의 대사나 장면 묘사 프롬프트를 대량으로 확보하기 위해 LLM으로 합성 데이터를 생성하거나, 추후 사용자가 만화를 '저장'하거나 '다시 생성'하는 행동을 사용자 피드백으로 삼아 RAG 검색 품질을 평가하는 전략을 적용할 수 있습니다.



2. 수동 레이블링의 5단계 프로세스 중 "골드 표준 데이터셋"은 왜 필요한가요? 이것 없이 외주를 맡기면 어떤 문제가 생기나요?
- 필요성: 엔지니어가 직접 작업한 소량의 명확한 기준 데이터셋으로, 여러 레이블러의 작업 결과(품질 및 일치도)를 객관적으로 평가하는 기준점이 되기 때문입니다.

- 발생하는 문제: 골드 표준 없이 외주를 맡기면, 데이터의 모호한 상황에 대해 레이블러마다 각기 다른 잣대로 해석하게 되어 큰 비용을 쓰고도 일관성 없고 품질이 낮은 데이터셋을 얻게 됩니다.

3. 약지도 학습이 수동 레이블링 대비 갖는 가장 큰 장점을 "유지보수" 관점에서 설명해 보세요. 레이블 체계가 변경되었을 때 각각 어떤 일이 벌어지나요?
- 가장 큰 장점: 직관적인 규칙(휴리스틱)을 레이블링 함수(코드) 형태로 작성하기 때문에, 수정 사항이 생겨도 유연하고 즉각적인 대처가 가능합니다.

- 수동 레이블링 시: 데이터 스키마(분류 기준)가 변경되면, 보유한 모든 데이터를 처음부터 사람이 일일이 다시 레이블링해야 합니다.

- 약지도 학습 시: 데이터 스키마가 변경되어도 기존 레이블링 함수(코드)의 조건만 수정한 후 스크립트를 재실행하면, 수백만 개의 데이터를 즉시 새로운 체계에 맞게 갱신할 수 있습니다.


4. LLM을 이용한 합성 데이터 생성이 효과적인 상황과 주의해야 할 점은 무엇인가요?
- 효과적인 상황: 특정한 의도나 형식을 갖춘 대규모 Fine-tuning 데이터셋이 필요할 때(예: 고객 문의 응답 1,000개 생성), 프롬프트만으로 레이블링 비용 없이 빠르게 데이터를 구축할 수 있어 효과적입니다.

- 주의해야 할 점: LLM이 생성한 내용이 항상 정확하거나 유효한 것은 아니므로, 생성된 합성 데이터의 품질을 검증하는 별도의 절차가 반드시 포함되어야 합니다.



✅ Chapter 12 체크포인트

1. 데이터 버전 관리의 4단계 중 자신의 현재 프로젝트는 어느 레벨에 해당하나요? 한 단계 올리려면 구체적으로 무엇을 해야 하나요?
: RAG 기반 4컷 만화 생성 파이프라인 프로젝트를 기준으로 본다면, 프로토타이핑 단계 특성상 Level 0(무관리) 또는 Level 1(단순 스냅샷)에 해당할 가능성이 높습니다. 이를 Level 2(코드로서의 데이터)로 한 단계 올리려면, 무거운 원본 데이터(만화 이미지, RAG용 원본 문서 등)는 S3와 같은 객체 저장소에 분리하여 저장하고, 해당 데이터의 URL과 라벨(프롬프트)이 기록된 메타데이터 파일(Parquet/JSON)만 Git LFS로 추적하도록 구조를 개편해야 합니다.

2. "코드 + 데이터 = 모델"이라는 공식에서, 데이터 버전 관리 없이 모델을 롤백하려 할 때 어떤 문제가 발생하는지 구체적인 시나리오를 그려보실 수 있나요?
: 만화 생성 결과물의 품질이 갑자기 저하되어 코드를 지난주 버전으로 롤백하더라도, 그사이 RAG 검색용 벡터 DB에 노이즈 데이터가 유입되었거나 프롬프트 데이터셋 자체가 변경되었다면 성능은 원래대로 복구되지 않습니다. 데이터의 버전이 기록되어 있지 않으므로 "정상 작동하던 지난주의 정확한 데이터 상태"를 재현할 방법이 없어, 코드 문제인지 데이터 문제인지 원인을 파악하고 해결할 수 없게 됩니다.

3. Level 2("코드로서의 데이터")의 "장부" 비유를 자신의 언어로 다시 설명할 수 있으신가요?
: 용량이 큰 실제 데이터 파일(이미지, 텍스트 원본)은 외부 저장소(S3)에 보관하고, 버전 관리 시스템(Git)에는 "어떤 파일이 저장소의 어느 주소(URL)에 위치해 있는지" 텍스트로 기록된 가벼운 인덱스 파일(장부)만 올려서 추적하는 방식입니다. 특정 Git 커밋 시점으로 이동하면 이 장부 파일을 통해 당시의 데이터 구성 상태를 정확히 파악하고 동기화할 수 있습니다.

4. 워크플로우 자동화가 필요해지는 시점은 언제인가요? "단순한 파이썬 스크립트"로 충분한 경우와, Airflow 같은 전문 도구가 필요한 경우를 구분할 수 있으신가요?
- 단순한 파이썬 스크립트가 충분한 경우: 단일 장비(PC) 자원으로 처리가 가능하고, 실행 흐름이 단순하며, 작업 실패 시 엔지니어가 수동으로 스크립트를 다시 실행해도 비즈니스에 무리가 없는 소규모 단발성 데이터 처리 작업일 때 적합합니다.

- Airflow 등 전문 도구가 필요한 경우: 데이터 추출, 전처리, 학습 등 여러 작업 단계(DAG) 간에 엄격한 선후 의존성이 존재하여, 앞 단계가 실패할 경우 뒷 단계를 자동으로 중단하고 재시도하는 로직이 필요할 때 도입합니다. 매일 특정 시간에 RAG 검색 DB를 갱신하는 것처럼 파이프라인이 사람의 개입 없이 안정적으로 구동되어야 하는 서비스 환경에 필수적입니다.



✅ Day 2 통합 체크포인트 — 오늘 배운 것을 하나로 꿰기

1. 환경 점검: 여러분이 지금까지 실습에 사용한 환경을 떠올려 보세요. 재현 가능한 환경 구축(결정적 빌드)이 되어 있었나요? 팀원에게 동일한 환경을 전달하려면 어떤 파일들이 필요한가요?

- 현재 상태: 단순한 pip install 방식이나 노트북 환경에 의존했다면 완벽한 결정적 빌드(재현성)가 보장되지 않은 상태입니다.

- 필요한 파일: 팀원에게 동일한 환경을 전달하려면 개발자가 직접 지정한 핵심 라이브러리 목록인 requirements.in과, 이를 바탕으로 모든 하위 의존성 버전을 정확히 고정한 requirements.txt(또는 uv.lock) 파일이 필요합니다. 추가로 환경 구축 명령어를 자동화한 Makefile을 함께 전달하면 좋습니다.


2. 코드 리팩토링 계획: 지금까지 작성한 PyTorch 학습 코드 중 하나를 골라, Lightning으로 리팩토링한다면 어떤 부분이 LightningModule로, 어떤 부분이 Trainer 설정으로 분리될지 구체적으로 구상해 보세요. training_step, validation_step, configure_optimizers 각각에 무엇이 들어가나요?

- LightningModule: "무엇을" 학습할지 정의합니다.

	- training_step: 입력 데이터 순전파, 손실(Loss) 계산, 모델 파라미터 업데이트를 위한 최종 손실값 반환 및 스텝별 로깅(train_loss).

	- validation_step: 손실 및 평가 지표(Accuracy 등) 계산, 에포크 단위 집계를 위한 로깅(val_loss, val_acc 등).

	- configure_optimizers: AdamW 같은 옵티마이저와 Cosine Annealing 등의 학습률 스케줄러 객체 반환.

- Trainer: "어떻게" 학습할지 정의하는 엔지니어링 설정을 담당합니다. 사용할 GPU 대수(devices), 혼합 정밀도(precision="16-mixed"), 분산 학습 전략(strategy="ddp"), 에포크 수, 체크포인팅 및 얼리 스토핑 콜백 등을 관리합니다.


3. 인프라 설계: Day 1에서 기획한 ML 프로젝트를 실행한다면, GPU는 무엇을 선택하고, 클라우드는 어디를 쓰며, 실험 관리는 어떤 도구를 사용할지 구체적으로 계획해 보세요. 예상 비용은 얼마인가요?

- GPU 선택: 이미지 생성 모델(Diffusion)이나 LLM 파인튜닝, RAG 벡터 검색을 빠르게 처리하기 위해 VRAM이 넉넉하고 메모리 대역폭이 넓은 A100(혹은 A6000 멀티 구성)을 선택합니다.

- 클라우드: 초기 실험 및 프로토타이핑 단계에서는 가성비가 좋은 RunPod이나 Lambda Labs를 활용하고, 서비스 배포가 가까워지면 GCP 등 대형 클라우드로 전환합니다.

- 실험 관리: 하이퍼파라미터(프롬프트 길이, 학습률 등) 튜닝과 시스템 메트릭 모니터링을 위해 Weights & Biases (W&B)를 도입하여 대시보드에서 결과를 통합 비교합니다.


4. 데이터 전략: 같은 프로젝트의 데이터를 어떻게 확보할 것인가요? 레이블링을 최소화하는 전략 중 적용 가능한 것은 무엇이며, 데이터 버전 관리는 어느 레벨부터 시작할 것인가요?

- 레이블링 최소화 전략: 대량의 프롬프트와 장면 묘사 데이터셋을 확보하기 위해 강력한 LLM(예: GPT-4o)을 활용하여 합성 데이터를 생성합니다. 서비스 오픈 후에는 사용자가 만화를 '저장'하거나 '재생성'하는 로그를 사용자 피드백으로 삼아 모델을 개선합니다.

- 데이터 버전 관리: 무거운 원본 이미지 파일이나 벡터 데이터는 S3에 올리고, 텍스트 형태의 프롬프트 메타데이터와 파일 URL만 Git LFS로 추적하는 Level 2 (코드로서의 데이터) 단계부터 시작합니다.


5. 비용 시뮬레이션: 위 프로젝트의 학습에 필요한 GPU 시간을 대략적으로 추산하고, 클라우드 비용을 "시간당"과 "실험당" 두 관점에서 비교해 보세요. 스팟 인스턴스를 쓸 수 있는 조건이 갖춰져 있나요?

- 비용 관점: 시간당 대여료가 저렴하지만 느린 하급 GPU를 쓰는 것보다, 시간당 비용이 비싸더라도 연산 속도가 압도적인 A100 등을 단시간에 사용하는 것이 "실험당 총비용"을 크게 낮추고 개발 사이클을 단축합니다.

- 스팟 인스턴스 조건: 저렴한 스팟 인스턴스를 사용하려면 인스턴스 회수 시 학습 진행 상황을 잃지 않아야 합니다. 코드를 PyTorch Lightning으로 리팩토링하면서 ModelCheckpoint 콜백을 통해 가중치와 옵티마이저 상태를 자동 저장(체크포인팅)하도록 설정했다면, 스팟 인스턴스를 활용할 완벽한 조건이 갖춰진 것입니다.
