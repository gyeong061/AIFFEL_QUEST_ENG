✅ Chapter 0 체크포인트

1. 모델 배포(FastAPI/Streamlit)와 Full Stack DL, 그리고 MLOps는 각각 어떤 범위를 담당하며, 왜 세 과정이 분리되어야 하는지 설명할 수 있으신가요?

- 모델 배포(FastAPI/Streamlit): 학습이 완료된 모델을 사용자가 접근하고 사용할 수 있도록 엔드포인트와 인터페이스를 제공하는 '서빙(Serving)' 영역을 담당합니다.

- Full Stack DL: 모델이 실제 비즈니스 문제를 올바르게 풀고 있는지, 데이터는 신뢰할 수 있는지 등 기획부터 운영까지 모델의 '생애 전체를 관리하는 제품 중심적 사고방식'을 담당합니다.

- MLOps: 컨테이너화(Docker), 워크플로우 자동화, 파이프라인 구축(CI/CD) 등 모델을 안정적으로 운영하고 재학습시키기 위한 '인프라 및 자동화 규율'을 담당합니다.

- 분리 이유: 각 과정의 초점과 지향점이 다르기 때문입니다. 모델 배포는 완성된 결과물의 '전달'에, Full Stack DL은 제품과 데이터의 '생애주기 기획'에, MLOps는 이를 기술적으로 지탱하는 '인프라 및 운영 체계'에 집중해야 전체 ML 시스템이 기술적 부채 없이 안정적으로 순환할 수 있습니다.


2. "평평한 지구 ML"과 "둥근 지구 ML"의 차이를 동료에게 30초 안에 설명할 수 있으신가요? 데이터 플라이휠은 이 비유에서 어디에 해당하나요?

- 평평한 지구 ML: ML 워크플로우를 직선적(Linear)으로 보며, 모델이 목표 성능을 달성해 배포되면 프로젝트가 종료된 것으로 간주하는 관점입니다.

- 둥근 지구 ML: 배포를 끝이 아닌 새로운 시작(Outer Loop)으로 보며, 실제 사용자의 데이터가 피드백되어 지속적으로 모델을 개선하는 순환적인 관점입니다.

- 데이터 플라이휠의 위치: 둥근 지구 비유에서 데이터 플라이휠은 사용자의 행동(데이터)이 모델을 개선하고, 개선된 모델이 더 나은 경험을 제공해 더 많은 데이터를 모으게 만드는 '순환 구조의 핵심 엔진'에 해당합니다.


3. ML Powered Product와 MLOps의 지향점 차이를 구체적인 질문 하나씩으로 대비할 수 있으신가요?

- ML Powered Product의 지향점 질문: "사용자가 모델과 어떻게 상호작용하며, 데이터 레이블링과 사용자 피드백을 제품 설계에 어떻게 녹여낼 것인가?" (제품 맥락, 사용자 경험 중심)

- MLOps의 지향점 질문: "모델을 안정적으로 서빙하고, 지속적으로 자동 재학습시키는 파이프라인을 어떻게 만들 것인가?" (인프라, 확장성, 자동화 중심)



✅ Chapter 1 체크포인트

1. Software 1.0과 Software 2.0의 근본적인 차이는 무엇이며, 이 차이가 왜 전혀 다른 개발·테스트·운영 전략을 요구하는지 설명할 수 있으신가요?

- 근본적 차이: Software 1.0은 프로그래머가 직접 명시적인 로직(if-else)을 작성하여 입력과 출력의 관계를 정의합니다. 반면, Software 2.0은 개발자가 데이터와 목적 함수만 정의하면, 최적화 알고리즘이 데이터를 바탕으로 스스로 입출력 관계를 학습하여 코드를 만들어냅니다.

- 다른 전략이 필요한 이유: ML 제품은 단순히 작성된 '코드'뿐만 아니라 데이터의 품질과 분포에 의해 실제 동작이 결정되기 때문입니다. 데이터가 변하면 동작도 변하므로, 기존 소프트웨어와는 전혀 다른 개발, 테스트, 운영 방식이 요구됩니다.



2. CACE 현상(Changing Anything Changes Everything)이 전통적인 소프트웨어에서는 왜 덜 문제가 되고, ML 시스템에서는 왜 치명적인지 정리해 보셨나요?

- 전통적인 소프트웨어는 모듈 간의 경계가 명확하여 일부 코드를 수정해도 diff로 쉽게 추적하고 독립적으로 테스트할 수 있습니다.

- 하지만 ML 시스템에서는 데이터 파이프라인의 작은 포맷 변경이나 모델의 파라미터 하나만 바뀌어도 전체 시스템의 예측 결과가 어떻게 변할지 예측하기 어렵습니다. 컴포넌트 간의 경계가 허물어져 있어 독립적인 유지보수와 롤백이 극도로 까다로워지기 때문에 훨씬 치명적으로 작용합니다.



3. "기술의 범용화(Commoditization)"가 ML 엔지니어의 역할을 어떻게 변화시키고 있는지 자신의 언어로 설명할 수 있으신가요?

- Hugging Face와 같은 라이브러리의 발전과 OpenAI API 등 Model-as-a-Service의 폭발적인 성장으로 인해, 최첨단 모델을 단 몇 줄의 코드로 호출하거나 오픈소스 모델을 쉽게 활용할 수 있게 되었습니다.

- 이로 인해 과거 "모델을 밑바닥부터 학습시키고 최적화하는 사람"이었던 ML 엔지니어의 역할은, "Foundation Model을 제품에 통합하고, 전체 시스템의 데이터 플라이휠을 기획 및 관리하는 사람"으로 범위가 넓어지고 패러다임이 변화하고 있습니다.




✅ Chapter 2 체크포인트

1. 현재 구상하고 계신 (혹은 관심 있는) ML 프로젝트를 실현 가능성 × 임팩트 매트릭스에 배치해 보셨나요? 어느 사분면에 위치하나요?
ML 프로젝트의 실현 가능성 × 임팩트 매트릭스 배치 (일반적인 예시: 이커머스 상품 리뷰 요약 시스템)

- 구상 중인 프로젝트가 '수만 개의 상품 리뷰를 분석해 핵심 장단점 3줄로 요약해 주는 기능'이라고 가정할 때, 이 프로젝트는 '높은 실현 가능성(High Feasibility)과 높은 비즈니스 임팩트(High Impact)' 사분면(우상단)에 위치합니다.

- 실현 가능성: 최신 LLM(대형 언어 모델) API를 활용하면 텍스트 요약 및 감성 분석을 높은 정확도로 수행할 수 있으므로 기술적 구현 난이도가 낮습니다.

- 임팩트: 사용자가 수백 개의 리뷰를 읽는 시간을 단축시켜 구매 전환율을 높일 수 있으므로 비즈니스에 미치는 긍정적 효과가 큽니다.



2. Build vs. Buy vs. API 의사결정 트리에서, "API로 충분한가?"라는 질문에 답하기 위해 구체적으로 무엇을 확인해야 하는지 정리할 수 있으신가요?

- 성능 및 목적 적합성: 풀고자 하는 문제(예: 일반적인 텍스트 요약, 감성 분석)가 Foundation Model API(GPT-4o, Claude 등)의 기본 능력만으로도 목표 정확도를 달성할 수 있는지 확인합니다.

- 운영 비용(Cost): 예상되는 일일 트래픽을 기준으로 토큰당 API 호출 비용을 계산했을 때, 서비스 유지에 무리가 없는지 검토합니다.

- 지연 시간(Latency): 외부 서버를 거쳐오는 네트워크 응답 시간이 서비스에서 요구하는 최대 허용 대기 시간(SLA) 이내인지 확인합니다.

- 데이터 보안 및 프라이버시(Security): 처리해야 할 데이터에 민감한 개인정보(의료 기록, 금융 정보 등)나 기업 기밀이 포함되어 있어, 외부 서드파티 서버로 데이터를 전송하는 것이 규제에 위반되지 않는지 판단합니다.



3. ML을 도입하기 전에 시도해야 할 4가지 대안을 나열하고, 각각이 더 적합한 상황을 예시와 함께 설명할 수 있으신가요?

- 규칙 기반 접근법 (Rule-based): 문제의 규칙이 명확하고 if-else 로직이나 정규 표현식으로 빠르게 해결할 수 있는 상황에 적합합니다. (예: 이메일 제목에 특정 스팸 키워드가 포함된 경우 차단하는 시스템)

- 사람의 판단 (Human-in-the-loop): 오판의 대가가 매우 크거나 책임 소재가 중요하여 기계에 완전히 위임할 수 없는 상황에 적합합니다. (예: 기업 간 대규모 인수합병(M&A) 계약서의 최종 법률 검토)

- Foundation Model API 활용: 자체 데이터를 처음부터 학습시킬 필요 없이 범용적인 언어 이해나 생성 능력이 필요한 상황에 적합합니다. (예: 서비스 소개 웹페이지의 다국어 번역 기능)

- 전통적 통계 기법: 인과관계나 변수 간의 영향력에 대한 명확한 해석(Explainability)이 필요하거나 데이터 구조가 단순한 경우에 적합합니다. (예: 과거 5년간의 월별 매출 데이터를 바탕으로 한 다음 분기 예산 예측)



✅ Chapter 3 체크포인트

1. ML 프로젝트 라이프사이클 4단계를 순서대로 말할 수 있으신가요? 각 단계의 핵심 활동을 한 문장으로 요약해 보세요.

- 1단계 (프로젝트 기획 및 설정): ML 도입 여부를 결정하고 문제 정의, 성공 지표, 리소스를 기획합니다.

- 2단계 (데이터 수집 및 레이블링): 모델 학습에 필요한 데이터를 수집 및 정제하고 레이블링 파이프라인을 구축합니다.

- 3단계 (모델 학습 및 디버깅): 베이스라인 모델을 구축한 후 최신 모델 적용과 하이퍼파라미터 튜닝을 통해 성능을 최적화합니다.

- 4단계 (배포 및 모니터링): 모델을 실제 환경에 배포하고 사용자 피드백을 수집하며 지속적인 성능 모니터링을 진행합니다.



2. "4단계 → 2단계 되돌아감"이 가장 흔한 이유는 무엇이며, 이를 미리 방지하기 위해 기획 단계에서 어떤 질문을 던져야 하는지 생각해 보셨나요?

- 이유: 오프라인 테스트에서는 잘 작동하던 모델이 실제 사용자 환경(프로덕션)에 배포된 후 성능이 급감하는 경우가 많으며, 이는 주로 학습 데이터에 없던 새로운 유형의 입력(데이터 분포 차이)이 발생하기 때문입니다. 이에 따라 실패 사례를 수집하고 다시 레이블링하기 위해 2단계로 복귀하게 됩니다.

- 방지 질문: 기획 단계에서 "우리가 수집할 수 있는 데이터가 실제 사용자가 서비스에서 입력할 데이터 분포와 완전히 일치하는가?", "실제 프로덕션 환경의 데이터를 초기부터 가장 가깝게 흉내 내어 수집할 방법은 무엇인가?"를 미리 질문하고 검증해야 합니다.



3. 데이터 플라이휠이 자연스럽게 형성되는 제품과 인위적으로 설계해야 하는 제품의 차이를 예시와 함께 설명할 수 있으신가요?

- 자연스럽게 형성되는 제품: 사용자가 제품의 핵심 기능을 이용하는 행위 자체가 모델 학습을 위한 완벽한 정답(Label) 데이터로 축적되는 시스템입니다.

예시: 넷플릭스나 유튜브의 추천 시스템 (사용자가 추천 영상을 클릭, 시청, 또는 스킵하는 행동 자체가 모델 평가를 위한 암묵적 피드백이 됨)

- 인위적으로 설계해야 하는 제품: 사용자의 사용 결과가 시스템에 직접적인 모델 평가 데이터로 돌아오지 않아, 서비스 내부에 명시적인 피드백 루프를 UI/UX 차원에서 추가해야 하는 시스템입니다.

예시: AI 챗봇이나 번역기 (번역 결과나 답변 하단에 '좋아요/싫어요(👍👎)' 버튼을 배치하거나, 답변의 '복사하기' 버튼 클릭 여부를 추적하도록 명시적으로 설계해야 데이터 축적이 가능함)

전통적 통계 기법: 인과관계나 변수 간의 영향력에 대한 명확한 해석(Explainability)이 필요하거나 데이터 구조가 단순한 경우에 적합합니다. (예: 과거 5년간의 월별 매출 데이터를 바탕으로 한 다음 분기 예산 예측)





✅ Chapter 4 체크포인트

1. 세 가지 아키타입(Software 2.0, Human-in-the-loop, Autonomous) 각각에 해당하는 실제 서비스를 하나씩 떠올려 보실 수 있나요?

- Software 2.0 (기존 자동화의 개선): 이커머스 플랫폼의 개인화 상품 추천 시스템입니다. 과거 담당자가 수동으로 기획전을 구성하거나 단순 판매량 기준으로 상품을 나열하던 방식을, 사용자의 클릭 및 구매 데이터를 학습한 ML 모델로 대체하여 효율을 높입니다.

- Human-in-the-loop (인간 판단 보조): 기업의 AI 기반 법률 문서(계약서) 리뷰 시스템입니다. AI가 수백 장의 계약서에서 독소 조항이나 누락된 필수 항목을 1차로 식별해 표시하면, 최종적으로 전문 변호사가 이를 검토하여 승인합니다.

- Autonomous (완전 자율 시스템): 로보어드바이저를 활용한 알고리즘 자동 매매 시스템입니다. 시장 데이터를 실시간으로 분석하여 사람의 개입 없이 최적의 타이밍에 주식을 매수하고 매도하는 의사결정을 독립적으로 수행합니다.



2. 하나의 제품이 처음에는 Human-in-the-loop으로 시작하여 Autonomous로 진화하는 경로를 구체적으로 그려볼 수 있으신가요? 전환의 조건은 무엇일까요?

- 진화 경로 (고객 센터 챗봇 예시): 초기에는 AI가 고객 문의를 분석해 답변 초안을 작성하고 상담원이 이를 검토 및 수정하여 발송합니다(Human-in-the-loop). 운영을 통해 특정 단순 문의 유형(예: 단순 배송 조회, 환불 규정 안내)에서 AI 초안이 수정 없이 채택되는 비율이 압도적으로 높아지면, 해당 카테고리에 한정하여 사람의 검토 단계를 생략하고 모델이 직접 즉시 답변하도록(Autonomous) 파이프라인을 전환합니다.

- 전환 조건: 모델 예측의 신뢰도(Confidence score)가 목표 임계치를 지속적으로 상회할 때, 예외 상황(Edge case)에 대한 방어 로직이 충분히 확보되었을 때, 그리고 오작동 시 발생하는 비즈니스적 실패 비용(Cost of Failure)이 수용 가능한 수준일 때 전환합니다.



3. 자신이 만들고 싶은 ML 제품은 어떤 아키타입에 해당하며, 그에 따라 모델 정확도·실패 비용·데이터 플라이휠 전략이 어떻게 달라지는지 정리해 보셨나요?

-> 1) AI 서류 심사 보조 시스템

- 해당 아키타입: 수천 장의 이력서를 분석해 채용 담당자의 검토 시간을 줄여주는 Human-in-the-loop에 해당합니다. AI가 직무 적합도를 점수화하고 핵심 역량을 요약하지만, 면접 대상자를 선정하는 최종 결정은 사람이 수행합니다.

- 모델 정확도 요구사항: 특정 지원자를 부당하게 누락시키지 않아야 하므로, 편향(Bias)이 없고 직무 역량 추출에 특화된 높은 정확도가 요구됩니다.

- 실패 비용: 훌륭한 인재를 놓치거나 채용 차별 논란이 발생할 경우 윤리적, 비즈니스적 타격(실패 비용)이 매우 큽니다. 따라서 인간의 최종 검토 단계를 쉽게 제거할 수 없습니다.

- 데이터 플라이휠 전략: 시스템 내부 UI에 채용 담당자가 AI의 평가 점수를 수동으로 조정하거나, AI가 기각한 지원자를 합격시키는 기능을 배치합니다. 이처럼 담당자가 시스템과 상호작용하는 행동(수정 내역) 자체가 정답 레이블로 축적되어, 기업별 인재상에 맞춰 모델이 정교하게 재학습되는 구조를 그립니다.

-> 2) 기구 없는 홈 필라테스 및 요가 애플리케이션의 아키타입 및 전략 적용

해당 아키타입: 스마트폰 카메라로 자세를 추정해 실시간 교정 피드백을 주는 Autonomous를 궁극적으로 지향하되, 부상 방지를 위해 초기에는 사용자의 명시적 통증 확인이나 필요시 전문 강사의 비동기 리뷰가 개입하는 Human-in-the-loop 요소를 강하게 결합해야 합니다.

모델 정확도: 매우 높은 수준이 요구됩니다. 잘못된 각도나 정렬 피드백은 사용자의 근골격계 통증 악화나 부상으로 직결될 수 있기 때문입니다.

실패 비용: 신체적 부상이라는 높은 실패 비용을 동반합니다. 따라서 카메라 사각지대나 조명 문제로 모델의 자세 인식 신뢰도가 떨어질 경우, 억지로 교정 지시를 내리기보다 "정확한 인식이 어렵습니다. 안전을 위해 기본 준비 자세로 돌아가주세요"라고 안내하는 보수적인 방어(Failover) 로직이 필수적입니다.

데이터 플라이휠 전략: 홈 트레이닝 환경 특성상 AI의 피드백이 실제로 올바르게 작용했는지 시스템이 스스로 알기 어렵습니다. 따라서 특정 동작 세트가 끝난 직후 UI 상에 "통증 없이 목표 근육에 자극이 잘 왔나요?"라는 체크 기능을 인위적으로 설계해야 합니다. 사용자가 입력하는 이 주관적인 신체 피드백이 곧 정답(Label) 데이터로 축적되어, 개인의 체형과 보상 작용 패턴에 맞춘 모델 재학습 플라이휠을 돌리게 됩니다.

1. ML 프로젝트에 필요한 5가지 역할을 나열하고, "풀스택 ML 엔지니어"가 이 중 어디까지 커버할 수 있는지 설명할 수 있으신가요?

- 풀스택 ML 엔지니어의 커버 범위: Foundation Model API와 각종 오픈소스 프레임워크의 발전으로 인해, 풀스택 ML 엔지니어는 과거 분리되어 있던 '모델 개발(ML 엔지니어)'을 넘어, 기초적인 '데이터 파이프라인 구축(데이터 엔지니어의 일부)'과 FastAPI/Streamlit 등을 활용한 '프로토타입 배포 및 서빙(ML Platform 엔지니어의 일부)'까지 매우 넓은 영역을 혼자서 커버할 수 있게 되었습니다. 이를 통해 소규모 팀 단위에서도 아이디어 기획부터 모델 배포까지 전체 사이클을 빠르게 실행할 수 있습니다.


2. "리서치와 프로덕션의 거리를 좁혀라"는 원칙이 구체적으로 팀의 일하는 방식에 어떤 변화를 요구하는지 생각해 보셨나요?

- 기존처럼 '모델을 연구하고 만드는 사람'과 '그 모델을 넘겨받아 실제 서비스 인프라에 올리는 사람'이 분리되어 일할 때 발생하는 소통의 벽과 마찰을 없애야 한다는 것을 의미합니다.

- 구체적인 업무 방식의 변화로는, 모델을 만든 엔지니어가 단순히 주피터 노트북 환경에서 실험을 끝내는 것이 아니라, 직접 FastAPI나 Streamlit 같은 도구를 활용해 작동 가능한 데모를 만들고 배포해 보아야 합니다. 모델 개발자가 직접 프로덕션과 유사한 환경을 다뤄봄으로써 이해관계자들에게 빠르게 결과물을 보여주고 피드백을 받는 민첩한(Agile) 업무 흐름이 요구됩니다.

1. 프로젝트 시작 전 필수 질문 10가지 중, 자신의 프로젝트에서 가장 답하기 어려운 3개는 무엇이며 왜 어려운지 정리해 보셨나요?

-> AI 고객 센터 챗봇 시스템 기준

- 실패 비용 (7번): 챗봇이 환불 규정이나 약관에 대해 잘못된 정보(할루시네이션)를 제공할 경우, 고객 불만족을 넘어 법적 분쟁이나 심각한 브랜드 신뢰도 하락으로 이어질 수 있습니다.


-> 홈 필라테스 앱 기준

데이터 및 라벨링 (4, 5번): 사용자의 체형, 유연성, 근골격계 정렬 상태가 모두 다르기 때문에 '완벽한 정답(Ground Truth) 자세'를 일률적으로 정의하기 까다롭습니다. 전문가(물리치료사, 강사)의 교차 검증이 필요해 라벨링 확보 비용이 높습니다.

실패 비용 (7번): AI가 잘못된 보상 작용을 인지하지 못하고 '올바른 자세'로 잘못 피드백할 경우, 사용자의 통증 악화나 부상으로 이어질 수 있어 실패 시의 물리적/비즈니스적 리스크가 큽니다.

성공 지표 (2번): 사용자의 '통증 감소'나 '안전한 근력 강화'는 단기적으로 측정하기 어려운 정성적 지표입니다. 모델의 예측 성능 향상이 실제 건강 개선으로 이어졌는지 즉각적으로 확인할 프록시(Proxy) 메트릭을 설계하기 어렵습니다.



2. 고임팩트 프로젝트를 찾는 4가지 멘탈 모델(예측 비용 하락, 마찰 감소, Software 2.0, 업계 벤치마킹)을 자신의 도메인에 각각 적용해 보실 수 있나요?

- 마찰 감소: 고객이 복잡한 ARS 메뉴를 듣고 기다리거나, 긴 FAQ 문서를 직접 검색해야 하는 번거로움(마찰)을 없애고 자연어로 즉시 원하는 답을 얻게 합니다.

- Software 2.0: 기존 챗봇의 거대하고 복잡한 수동 규칙(if-else 및 키워드 매칭 기반의 시나리오 트리)을 LLM의 자연어 이해 능력으로 대체하여 시스템을 훨씬 유연하고 깔끔하게 만듭니다.

3. "정확도에 9를 하나 더 추가하면 비용이 10배 증가한다"는 법칙이 자신의 프로젝트에 어떤 의미를 갖는지 생각해 보셨나요? 요구 정확도를 낮출 수 있는 제품 설계 방법은 없을까요?

- 의미: 챗봇이 흔한 질문에 대해 90%의 정확도로 답변하도록 만드는 것은 API 연동만으로도 비교적 쉽습니다. 하지만 아주 드물게 발생하는 예외적인 클레임까지 포함해 99.9%의 정확도를 달성하려고 하면, 방대한 엣지 케이스(Edge Case) 데이터를 수집하고 파인튜닝을 반복해야 하므로 비용과 개발 기간이 천문학적으로 늘어납니다.

- 요구 정확도를 낮추는 제품 설계: 모든 질문에 완벽히 대답하려 하지 않고, 모델의 확신도(Confidence)가 낮거나 특정 키워드(예: '고소', '보상')가 감지되면 즉시 "해당 건은 상세 확인이 필요하여 전문 상담원에게 연결해 드리겠습니다"라고 안내하며 인간 상담원에게 자연스럽게 이관(Hand-off)하는 UX를 설계합니다.



4. "당신은 구글이 아니다"라는 원칙에 비추어, 자신의 프로젝트에서 지금 당장 필요한 도구와 나중에 도입해도 되는 도구를 구분할 수 있으신가요?

- 지금 당장 필요한 도구: 상용 Foundation Model API(GPT-4o, Claude 등), 내부 이해관계자에게 아이디어를 빠르게 보여줄 수 있는 Streamlit 데모, 그리고 초기 피드백 텍스트를 저장할 단순한 데이터베이스(PostgreSQL 등). (PoC 단계)

- 나중에 도입해도 되는 도구: 초당 수만 건의 트래픽을 처리하기 위한 Kubernetes 기반의 오토스케일링 인프라, 수백 개의 모델 버전을 관리하는 무거운 MLOps 플랫폼, 복잡한 실시간 A/B 테스트 프레임워크. (서비스가 실제로 성공하여 트래픽이 폭발할 때 도입합니다.)




✅ Day 1 통합 체크포인트 — 오늘 배운 것을 하나로 꿰기

1. 파이프라인 위치 인식: "모델 배포 → Full Stack DL → MLOps"라는 3단계 학습 경로에서, 오늘 다룬 내용이 왜 모델 배포 직후이자 MLOps 직전에 위치해야 하는지를 자신의 언어로 설명할 수 있으신가요?

모델 배포는 완성된 모델을 서빙하는 '단일 시점'의 작업입니다. 배포 직후 프로덕션 환경에서는 예상치 못한 데이터 입력이나 사용자 피드백 등 다양한 변수가 발생합니다. 따라서 자동화된 인프라(MLOps)를 구축하기 전에, 이 모델이 실제 비즈니스 가치를 창출하는지, 데이터 플라이휠을 어떻게 돌릴 것인지 제품 관점에서 기획하는 Full Stack DL 단계가 반드시 선행되어야 합니다. 이 기획이 탄탄해야만 기술적 부채를 최소화하는 올바른 MLOps 인프라를 세울 수 있습니다.


2. 종합 기획: 관심 있는 ML 프로젝트 하나를 선택하여, 오늘 배운 프레임워크를 순서대로 적용해 보세요. (1) ML이 정말 필요한가? → (2) Build/Buy/API 중 무엇? → (3) 아키타입은? → (4) 실현 가능성 × 임팩트는? → (5) 비용의 3대 동인은? → (6) PoC 종료 조건은?

-> 이커머스 AI 고객 센터 챗봇 기준

- (1) ML이 정말 필요한가?: 단순 키워드 매칭(규칙 기반)으로는 고객의 복잡한 환불/클레임 의도를 파악하기 어려우므로 자연어 처리 능력을 갖춘 ML이 필요합니다.

- (2) Build/Buy/API 중 무엇?: 처음부터 자체 모델을 학습시키기보다, 범용적인 텍스트 이해 능력이 뛰어난 상용 LLM(GPT-4o, Claude 등)을 활용하는 API 방식이 초기 비용과 속도 면에서 적합합니다.

- (3) 아키타입은?: AI가 답변 초안을 쓰고 상담원이 승인하는 Human-in-the-loop으로 시작하여, 단순 문의(배송조회 등)에 한해 즉시 답변하는 Autonomous로 점진적 전환합니다.

- (4) 실현 가능성 × 임팩트는?: LLM API의 발달로 기술적 구현이 쉬워 실현 가능성이 높고(High Feasibility), 상담원의 단순 업무를 줄여주므로 비즈니스 임팩트도 높습니다(High Impact).

- (5) 비용의 3대 동인은?: 기업 내부 정책 및 매뉴얼 데이터 큐레이션 비용(데이터 가용성), 할루시네이션(거짓 정보)을 방지하기 위한 안전장치 설계(정확도 요구사항), 프롬프트 엔지니어링 및 RAG 파이프라인 구축(문제 난이도).

- (6) PoC 종료 조건은?: "과거 고객 문의 샘플 100건에 대해, 챗봇이 80% 이상의 정확도로 올바른 매뉴얼을 참조하여 답변 초안을 생성하는가?"


-> 기구 없는 홈 필라테스 및 요가 앱 프로젝트 기준

- (1) ML이 필요한가?: 단순 각도 계산(규칙 기반)만으로는 다양한 체형과 복잡한 보상 작용을 실시간으로 파악하기 어려우므로, Vision AI 기반의 포즈 추정(Pose Estimation) ML 모델이 필수적입니다.

- (2) Build/Buy/API?: 비디오 스트리밍을 외부 서버로 보내면 지연 시간(Latency)과 개인정보 문제가 발생하므로, 모바일 기기(On-device)에서 돌아가는 경량화 오픈소스 모델(예: MediaPipe)을 활용하고 자체 데이터를 파인튜닝하는 Buy(오픈소스 활용) 전략이 적합합니다.

- (3) 아키타입: 궁극적으로 Autonomous(실시간 자동 교정)를 지향하나, 초기에는 치명적인 오류를 막기 위해 사용자의 명시적 통증 피드백이나 전문가 리뷰가 개입하는 Human-in-the-loop을 결합합니다.

- (4) 실현 가능성 × 임팩트: 기존 SOTA 비전 모델이 존재하여 실현 가능성이 높고(우측), 시간과 공간의 제약 없이 안전한 운동을 제공하므로 비즈니스 임팩트도 높습니다(상단). (High Feasibility, High Impact)

- (5) 비용의 3대 동인: 다양한 체형과 조명 환경에서의 자세 데이터 확보 비용(데이터 가용성), 부상 방지를 위한 보수적인 오차 허용 범위 설정(정확도 요구사항), 모바일 실시간 처리 프레임 확보(문제 난이도).

- (6) PoC 종료 조건: "선정된 오픈소스 비전 모델이 모바일 환경에서 30fps 이상으로 작동하며, 주요 부상 위험 자세(예: 허리 과신전 등) 3가지를 90% 이상의 신뢰도로 감지하는가?"




3. 둥근 지구 설계: 위에서 선택한 프로젝트의 데이터 플라이휠을 구체적으로 그려 보세요. 사용자의 어떤 행동이 데이터가 되고, 그 데이터가 어떻게 모델을 개선하며, 개선된 모델이 어떻게 더 많은 사용자를 끌어들이나요?

사용자가 챗봇과 대화한 후 "답변이 도움이 되었나요? (👍/👎)" 버튼을 누르거나, 인간 상담원이 AI의 초안을 '수정'하여 발송하는 행위 자체가 모델 평가를 위한 정답(Label) 데이터로 축적됩니다. 이 피드백을 바탕으로 RAG 파이프라인의 검색 성능을 개선하거나 프롬프트를 고도화(재학습)합니다. 개선된 챗봇은 더 높은 비율로 고객의 문제를 즉각 해결하여 만족도를 높이고, 이는 더 많은 고객이 ARS 전화 대신 챗봇을 사용하게 만드는 강력한 선순환 엔진으로 작동합니다.


4. 실패 시나리오: 위 프로젝트가 실패한다면 가장 가능성 높은 원인은 무엇일까요? 기술적 비실현성, 프로덕션 전환 실패, 조직 공감대 부족, 작은 문제 해결 중 어디에 해당하며, 이를 사전에 방지하기 위해 기획 단계에서 무엇을 할 수 있을까요?

- 가장 가능성 높은 실패 원인: 테스트 환경과 실제 사용자 환경의 차이로 인한 '프로덕션 전환 실패'입니다. 실험실에서는 정제된 문장으로 테스트했으나, 실제 프로덕션에서는 오타, 비속어, 감정이 섞인 장문의 클레임 등 예상치 못한 데이터(Data Mismatch)가 입력되어 모델이 오작동할 확률이 높습니다.

- 사전 방지책: 기획 및 PoC 단계부터 가상의 정제된 데이터가 아닌, '실제 고객센터에 접수된 날것(Raw)의 과거 대화 로그'를 기반으로 베이스라인 모델을 테스트하고 엣지 케이스를 미리 파악해야 합니다.



5. 기술적 부채 예측: 이 프로젝트가 성공적으로 배포된 후 6개월 뒤, 어떤 종류의 기술적 부채가 쌓여 있을 것으로 예상되시나요? CACE, 데이터 드리프트, 외부 세계의 불안정성 중 어떤 것이 가장 위협적일까요?

가장 위협적인 요소는 '외부 세계의 불안정성(Data Drift)'입니다. 시간이 지나 회사의 환불 규정이 바뀌거나 새로운 시즌 상품이 대거 출시되면, 과거의 데이터로 세팅된 챗봇은 현재와 맞지 않는 잘못된 정보(할루시네이션)를 제공하게 됩니다. 외부 지식이나 비즈니스 정책 변화에 맞춰 참조 문서(DB)를 지속적으로 업데이트하고 모델의 답변 품질을 자동 모니터링하는 인프라(MLOps)가 구축되어 있지 않다면, 이는 매우 심각한 기술적 부채로 작용할 것입니다.
