
✅ Day 8 최종 체크포인트  
Q1. 본인의 프로젝트에서 Pydantic 검증은 어떤 잘못된 입력을 막아줍니까?  
: SummarizeRequest가 text의 최소 10자·최대 10,000자 제한을 검사하고, max_new_tokens는 10~128 범위의 정수만 받게 합니다. 형식이나 범위가 맞지 않으면 FastAPI가 요청을 실행하기 전에 422 Unprocessable Entity를 반환합니다. 모델 서비스에서도 토큰 수가 512개를 넘으면 추가로 422를 반환합니다.  
  
Q2. Depends(verify_api_key)를 제거하면 어떤 위험이 있습니까?  
: 누구나 /summarize를 호출할 수 있습니다. 무단 사용, CPU/GPU 자원 고갈, 대량 요청으로 인한 서비스 장애, 운영 비용 증가 위험이 생깁니다. 현재의 하드코딩 키는 학습용이고, 실제 서비스에서는 환경 변수·DB·키 만료·폐기 정책 등을 사용해야 합니다.  
  
Q3. run_in_executor를 사용한 이유는 무엇입니까?  
: 현재 프로젝트의 run_in_threadpool은 같은 목적입니다. 모델 추론은 오래 걸리는 동기 작업이므로, 이를 FastAPI의 비동기 이벤트 루프에서 직접 실행하면 다른 요청까지 멈출 수 있습니다. 별도 스레드에서 추론을 수행해 서버가 다른 요청과 오류 응답을 계속 처리하도록 합니다.  
  
Q4. Day 1~8 중 가장 많이 참고한 Day는 어디였습니까? 왜?  
: 본 프로젝트는 Day 6의 API Key 인증 모듈을 직접 재사용하고, Day 3의 비동기 추론 및 Pydantic 검증 개념, Day 5의 FastAPI–Streamlit 연동 및 오류 처리 방식을 결합하여 구현하였다.
  
Q5. 이 서비스를 실제로 배포하려면 추가로 무엇이 필요합니까? 
: HTTPS와 도메인, 환경 변수 기반 비밀키 관리, 키 발급·교체·폐기, 요청 횟수 제한, Docker 배포, GPU/메모리 자원 설정, 모델 캐시 저장소, 로그·모니터링·알림, 오류 추적, 자동 테스트·CI/CD, 개인정보 처리 정책이 필요합니다. 트래픽이 많다면 요청 큐와 여러 서버 인스턴스도 고려해야 합니다.

#### 회고  
허깅 페이스에서 https://huggingface.co/eenzeenee/t5-small-korean-summarization 모델을 가져와서 이번 과제를 진행했다.  
모델의 가중치 용량이 약 300MB 내외여서 코랩에서 조건에 적합했고, 한국어 요약 전용으로 미세조정(Fine-tuning)된 모델이라 목적에도 적합하여 선정하였다.  
프론트엔드는 처음에는 일반 입력 폼으로 만들었지만, 노션 미션을 보고 이후 st.chat_message, st.chat_input, st.session_state를 사용해 채팅형 UI로 개선하였다.  
  
  
- Hugging Face의 한국어 T5 요약 모델을 FastAPI와 Streamlit으로 연결해 텍스트 요약 서비스를 구현  
단순히 모델을 실행하는 것에서 끝나지 않고, API Key 인증, Pydantic 입력 검증, 비동기 추론 처리, Streamlit 오류 처리까지 하나의 서비스 흐름으로 구성  
- Day 6에서 구현한 verify_api_key()를 재사용하여 Depends(verify_api_key)로 요약 API를 보호  
-> 이를 인증이 없는 요청이나 잘못된 API Key를 401 Unauthorized로 처리  
 모델 추론처럼 시간이 걸리는 작업은 이벤트 루프를 막지 않도록 스레드 풀에서 실행했고, 동시에 많은 요청이 들어오는 상황은 429 응답으로 제어.  
- 구현 과정에서는 Hugging Face 모델과 transformers 버전 호환성 문제 발생.  
처음에는 Transformers 5 버전에서 토크나이저 오류가 발생했고, 오류 메시지를 확인한 뒤 모델 카드의 안내에 따라 Transformers 4 버전으로 조정하여 해결  
-> 라이브러리 설치가 완료되었다고 해서 항상 모델이 정상 실행되는 것은 아니며, 모델 카드·오류 로그·의존성 버전을 함께 확인 필요  
- 백엔드 연결 실패, 시간 초과, 인증 실패, 입력 검증 실패 등의 상황을 사용자에게 이해하기 쉬운 문장으로 보여 주도록 구성  
- 결론적으로 모델 서빙은 모델 정확도뿐 아니라 인증, 입력 검증, 오류 처리, 사용자 경험, 라이브러리 버전 관리가 함께 갖춰져야 한다.   
추가적으로 필요한 부분은 실제 베포를 한다면 API Key를 코드에 직접 작성하지 않고 환경 변수나 데이터베이스에서 관리하며, HTTPS, 요청 횟수 제한, 로그 모니터링, Docker 기반 배포까지 추가 필요.
