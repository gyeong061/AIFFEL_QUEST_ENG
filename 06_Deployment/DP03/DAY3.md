✅ 체크포인트  
1. time.sleep(3)과 await asyncio.sleep(3)의 핵심 차이는 무엇입니까?  
- time.sleep(3)          → CPU를 3초간 점유. 그 동안 아무것도 할 수 없음.  
- await asyncio.sleep(3) → "3초 후에 깨워줘"라고 등록 후, 다른 작업 처리.   

async def   → "이 함수는 비동기 함수입니다" (중간에 멈췄다가 다시 실행될 수 있음)  
await       → "이 작업이 끝날 때까지 기다리되, 그 동안 다른 일을 해도 됩니다"  
 

2. 모델 추론처럼 CPU를 계속 사용하는 작업에서 async/await만으로 동시 처리가 안 되는 이유는 무엇입니까?  
: CPU가 끊임없이 일을 하고 있기 때문에 중간에 대기 시간이 없다. 그래서 단순한 async/await로는 이벤트 루프가 멈추는 현상을 피할 수 없으며, 이를 해결하기 위해서는 run_in_executor와 같이 연산을 별도의 스레드(Thread)로 넘기는 추가적인 패턴이 필요하다.  


✅ 체크포인트  
1. async def 안에서 time.sleep(3)을 호출하면 왜 다른 요청까지 지연됩니까?  
: async def로 선언한 함수 안에서 **동기 작업(모델 추론)**을 수행하면, 이벤트 루프가 그 작업이 끝날 때까지 멈춥니다. 멈춰 있는 동안 다른 요청은 처리되지 않습니다.  

2. 일반 def로 선언된 엔드포인트는 FastAPI가 내부적으로 어떻게 처리합니까?  
:  일반 def로 선언하면, FastAPI가 자동으로 별도 스레드에서 실행합니다. 하지만 이 방식은 스레드 수에 제한이 있어, 최적의 해결책은 아닙니다.  

3. blocking 추론 중 헬스체크까지 막히면 실무에서 어떤 문제가 발생할 수 있습니까?  
- 로드밸런서는 헬스체크로 서버 상태를 판단합니다.  
- 헬스체크가 응답하지 않으면 "서버 다운"으로 판단하여 트래픽을 차단합니다.  
- 실제로는 서버가 살아있는데, 추론 때문에 응답을 못 하는 것뿐입니다.  
- 결과적으로 정상 서버가 풀에서 빠지는 심각한 문제가 발생합니다.  


✅ 체크포인트  
1. run_in_executor가 이벤트 루프 블로킹을 방지하는 원리는 무엇입니까?  
: run_in_executor는 동기 함수를 별도 스레드(또는 프로세스)에서 실행하고, 그 결과를 비동기적으로 기다리는 패턴으로 이벤트 루프는 그동안 다른 작업을 처리하고 함수가 완료되면 결과를 반환한다.  

2. run_in_executor의 첫 번째 인자에 None을 넣으면 어떤 스레드풀이 사용됩니까?  
: 기본 스레드풀 사용  

3. 일반 def와 async def + run_in_executor의 핵심 차이는 무엇입니까?  
- __일반 def:__  
  → FastAPI 기본 스레드풀을 사용합니다.  
  → 스레드풀 크기를 제어할 수 없습니다.  
  → 다른 엔드포인트와 스레드풀을 공유합니다.  
  
- __async def + run_in_executor:__  
  → 추론 전용 스레드풀을 직접 만들어 사용합니다.  
  → 크기를 제어할 수 있습니다 (max_workers=4).  
  → 추론 부하가 다른 엔드포인트에 영향을 주지 않습니다.  

간단한 프로젝트에서는 일반 def로 충분하지만, 추론 전용 스레드풀을 분리하고 싶다면  run_in_executor를 사용합니다. 이 과정에서는 run_in_executor 패턴을 기본으로 사용합니다.  

4. GPU 추론 시 스레드풀 크기를 1~2로 제한하는 이유는 무엇입니까?  
: GPU는 물리적인 메모리 용량에 제한이 있고 내부적으로 병렬 처리하므로, 스레드를 늘려도 속도 향상이 크지 않습니다.

3. logging 모듈이 print()보다 나은 점은 무엇입니까?  
- print("에러 발생")           → 시간 정보 없음, 심각도 구분 없음, 파일 저장 불가  

- logger.error("에러 발생")    → 2024-01-15 14:30:22 ERROR [ml_api] 에러 발생   
                                        시간, 심각도, 모듈명이 자동 포함

: 이벤트 루프가 직접 실행하지 않고 별도의 스레드에서 실행

Q5. 글로벌 Exception Handler를 사용하는 이유는?  
1. 일관된 응답 규격 제공 (Consistency): 서버에서 에러가 발생했을 때 클라이언트(프론트엔드, 모바일 앱 등)에게 항상 동일한 구조의 에러 포맷(예: {"error_code": 400, "message": "잘못된 요청입니다."})을 보장합니다. 이를 통해 프론트엔드 측의 에러 처리 로직이 훨씬 단순해집니다.  

2. 관심사의 분리 (Separation of Concerns): 핵심적인 '비즈니스 로직'과 '예외 처리 로직'을 분리합니다. 개발자는 컨트롤러(라우터)에 비즈니스 로직만 집중해서 작성할 수 있어 코드 가독성이 크게 향상됩니다.  

3. 중복 코드 방지 (DRY 원칙): 모든 API 엔드포인트마다 try-catch 블록을 수십 번씩 반복해서 작성하는 비효율과 휴먼 에러를 방지합니다.  

4. 예상치 못한 에러의 최후 방어선 (Fallback): 개발자가 미처 예측하지 못해 개별적으로 처리하지 않은 런타임 에러(Unhandled Exception)가 발생하더라도, 글로벌 핸들러가 이를 최종적으로 가로채어 앱이 강제 종료되거나 톰캣/FastAPI 등의 기본 에러 화면이 날것으로 노출되는 것을 막아줍니다.  

Q6. 클라이언트에게 스택 트레이스를 노출하면 안 되는 이유는?  
1. 치명적인 보안 정보 유출 (Information Disclosure): OWASP(오픈소스 웹 애플리케이션 보안 프로젝트)에서도 강력히 경고하는 주요 보안 취약점입니다. 스택 트레이스에는 다음과 같은 민감 정보가 포함됩니다.  
- 서버의 물리적 디렉토리 파일 경로  
- 사용 중인 오픈소스 라이브러리와 프레임워크의 정확한 버전 정보  
- 데이터베이스 쿼리 구조 및 테이블명  
- 위험성: 공격자는 노출된 라이브러리 버전을 확인한 뒤, 해당 버전에 존재하는 알려진 취약점(CVE)을 이용해 맞춤형 해킹 공격(Targeted Attack)을 시도할 수 있습니다.  

2. 내부 아키텍처 및 로직 유출: 애플리케이션이 내부적으로 어떤 클래스와 메서드를 거쳐 데이터를 처리하는지, 기업의 내부 비즈니스 로직과 시스템 설계 구조가 외부(경쟁사 등)에 고스란히 노출됩니다.  

3. 사용자 경험(UX) 저하: 일반 사용자가 이해할 수 없는 수십 줄의 시스템 에러 코드가 화면에 출력되면, 서비스에 대한 신뢰도가 급격히 하락합니다. 클라이언트에게는 "일시적인 시스템 오류가 발생했습니다"와 같은 정제되고 친절한 메시지만을 제공해야 합니다.
