✅ 체크포인트  
1. Day 5(정형 데이터)와 Day 7(텍스트 생성)에서 전처리가 어떻게 다릅니까?  
: Day5는 정규화로 Day7은 토크나이저를 사용한다.  


2. Hugging Face Transformers 라이브러리의 역할은 무엇입니까?  
: Hugging Face 허브에 등록된 사전 학습된 대규모 언어 모델(본문의 경우 한국어 GPT 기반 모델)과 해당 모델의 토크나이저를 손쉽게 다운로드하고 로드하여 텍스트 생성 및 추론에 활용할 수 있도록 지원합니다. (본문 내 AutoTokenizer, AutoModelForCausalLM 활용)  


✅ 체크포인트  
1. 토크나이저의 encode()와 decode()는 각각 어떤 변환을 수행합니까?  
- encode(): 사람이 읽을 수 있는 일반 텍스트 문장을 모델이 연산하고 처리할 수 있는 숫자 배열(토큰 ID)로 변환합니다.  
- decode(): 모델이 추론을 통해 생성한 숫자 배열(토큰 ID)을 다시 사람이 읽을 수 있는 일반 텍스트로 변환합니다.  

2. model.generate()의 temperature 파라미터는 생성 결과에 어떤 영향을 줍니까?  
:텍스트 생성 시 결과의 무작위성(다양성)을 조절합니다.  

값이 낮을수록(0에 가까울수록) 가장 확률이 높은 단어만 선택하여 일관되고 예측 가능한 답변을 생성합니다. 반대로 값이 높을수록 확률이 다소 낮은 단어도 선택될 가능성이 커져, 더 다양하고 창의적인 텍스트가 생성됩니다.  

3. 멀티턴 대화에서 이전 대화 기록을 프롬프트에 포함하는 이유는 무엇입니까?  
: 언어 모델 자체는 과거의 입력이나 상태를 기억하지 못하는 무상태성(Stateless)을 가집니다. 따라서 모델이 대화의 흐름과 문맥(Context)을 이해하고 알맞은 답변을 생성하게 하려면, 사용자와 봇이 주고받은 이전 대화 기록 전체를 프롬프트에 묶어서 매번 새로 전달해야 합니다.  
  

✅ 체크포인트  
1. ChatRequest의 messages가 리스트인 이유는 무엇입니까?  
: 멀티턴 대화에서는 사용자와 봇이 주고받은 여러 번의 메시지 기록(턴)이 순차적으로 유지되어야 합니다. 전체 대화 내역을 순서대로 묶어 한 번에 전달하기 위해 리스트 형태를 사용합니다.  

2. 서버가 대화 기록을 저장하지 않고, 클라이언트가 매번 전체 기록을 보내는 이유는?  
: REST API의 무상태성(Stateless) 원칙을 따르기 때문입니다. 서버가 각 클라이언트의 상태(대화 기록)를 메모리에 유지하지 않아야 서버 확장이 용이하고 구조가 단순해집니다. 따라서 클라이언트가 스스로 대화 상태를 관리하고 매 요청 시 문맥 전체를 전달합니다.  

3. max_new_tokens을 너무 크게 설정하면 어떤 문제가 발생할 수 있습니까?  
- 응답 지연 및 자원 낭비: 텍스트를 길게 생성할수록 추론에 걸리는 시간이 길어져 사용자 응답 속도가 크게 느려지며, 서버의 컴퓨팅 자원을 과도하게 소모합니다.  

- 토큰 제한 초과: 누적된 대화 기록(프롬프트)과 생성할 토큰 수를 합친 값이 모델이 한 번에 처리할 수 있는 최대 컨텍스트 윈도우 크기(최대 길이 제한)를 초과하여 오류가 발생할 수 있습니다.  


✅ 체크포인트  
1. st.chat_message와 st.chat_input은 각각 어떤 역할을 합니까?  
- st.chat_message: 채팅 화면에서 사용자와 봇이 주고받은 메시지(말풍선 및 프로필 아이콘)를 시각적으로 렌더링하여 표시하는 역할을 합니다.  

- st.chat_input: 사용자가 새로운 텍스트 메시지를 입력하고 엔터를 눌러 전송할 수 있는 입력창 UI를 제공합니다.  

2. st.session_state["chat_messages"]에 대화 기록을 저장하는 이유는?  
: Streamlit 프레임워크는 사용자가 버튼을 누르거나 입력을 할 때마다 화면을 업데이트하기 위해 전체 코드를 처음부터 다시 실행(Rerun)하는 특성이 있습니다. 일반 변수에 대화 기록을 저장하면 화면이 새로고침될 때마다 데이터가 초기화되어 사라지므로, 재실행 간에도 데이터를 영구적으로 보존하기 위해 Streamlit의 상태 관리 객체인 st.session_state를 사용합니다.  


3. "대화 초기화" 버튼이 st.rerun()을 호출하는 이유는 무엇입니까?  
: 대화 기록을 담고 있는 리스트를 빈 리스트([])로 비워준 직후, 변경된 빈 상태를 즉시 화면에 반영하기 위해서입니다. st.rerun()을 호출하여 스크립트를 강제로 다시 실행해야 화면에 렌더링되어 있던 이전 채팅 내역들이 말끔히 지워집니다.  


✅ 체크포인트  
1. 챗봇 API에서 인증이 실패하면 서버는 어떤 상태 코드를 반환합니까?  
: 서버는 HTTP 401 (Unauthorized) 상태 코드를 반환합니다.

2. UI의 call_chat_api()는 401 응답을 받으면 사용자에게 무엇을 보여줍니까?   
: 사용자 화면에 "🔑 인증 실패. API Key를 확인하세요."라는 에러 메시지를 표시합니다.

3. Day 6의 인증 모듈(app/auth.py)을 Day 7에서 수정 없이 재사용할 수 있는 이유는 무엇입니까?  
: 인증 로직이 HTTP 헤더(X-API-Key)에 담긴 키를 검사하는 방식으로 동작하기 때문입니다. 클라이언트가 보내는 요청 데이터의 본문(Body)이 기존의 이미지 파일(UploadFile)에서 텍스트(JSON)로 바뀌었을 뿐, 헤더를 통한 인증 과정 자체는 동일하므로 코드를 그대로 재사용할 수 있습니다.


✅ Day 7 최종 체크포인트  
Q1. Day 5(정형 데이터)와 Day 7(텍스트 생성)에서 전처리 방식의 차이는?  
- Day 5 (정형 데이터): 수치형 데이터의 스케일을 맞추기 위해 평균(mean)과 표준편차(std)를 활용한 정규화를 수행합니다.  

- Day 7 (텍스트 생성): 사람이 작성한 텍스트 문장을 모델이 처리할 수 있는 숫자 형태(토큰 ID)로 변환하기 위해 토크나이저(BPE 등)를 사용합니다.  

Q2. 멀티턴 대화에서 서버가 상태를 유지하지 않는 이유는?  
:  REST API의 무상태성(Stateless) 원칙에 따르기 때문입니다. 서버가 각 클라이언트의 대화 기록을 메모리에 개별적으로 저장하고 유지하면 서버 확장이 어렵고 구조가 복잡해집니다. 따라서 클라이언트가 대화 내역 전체를 보관하고 매번 요청 시 서버에 전달하는 방식을 사용합니다.  

Q3. API Key가 잘못되면 서버는 어떤 상태 코드를 반환하고, UI는 어떻게 처리합니까?  
- 서버 반환: HTTP 401 Unauthorized 상태 코드를 예외(Exception)로 반환합니다.  

- UI 처리: Streamlit 프론트엔드에서 HTTPError를 예외 처리(catch)하여 상태 코드가 401인 경우, 사용자 화면에 "🔑 인증 실패. API Key를 확인하세요."라는 에러 메시지를 띄워줍니다.  

Q4. temperature를 낮추면 생성 결과에 어떤 변화가 있습니까?  
: 텍스트 생성 시 선택의 무작위성(다양성)이 줄어듭니다. 가장 확률이 높은 단어 위주로 선택하게 되므로, 더욱 일관적이고 예측 가능하며 보수적인 텍스트가 생성됩니다.  

Q5. 이 서비스를 다른 컴퓨터에서 실행하려면 무엇이 필요합니까?  
- Python 환경과 프로젝트에 사용된 필수 라이브러리(transformers, torch, fastapi, streamlit, uvicorn, requests 등) 패키지 설치가 필요합니다.  

- 개발된 백엔드(app/ 디렉터리 내의 파이썬 파일들)와 프론트엔드(frontend/ 디렉터리의 파이썬 파일) 소스 코드가 필요합니다. (사전 학습된 허깅페이스 모델은 코드 실행 시 ~/.cache/huggingface/에 자동으로 다운로드되므로 미리 가중치 파일을 옮길 필요는 없습니다.)
