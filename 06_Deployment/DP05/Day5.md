:입력은 주택 및 지역에 관한 8가지 숫자 데이터 (지역 가구 중위소득, 주택 평균 연식, 가구당 평균 방 개수, 가구당 평균 침실 개수, 지역 인구수, 가구당 평균 거주 인원, 위도, 경도)
출력은 모델이 예측한 주택 가격입니다.

2. MNIST 프로젝트와 비교했을 때, 데이터 형태가 어떻게 다릅니까?  
:
| 구분 | MNIST 프로젝트 | 주택 가격 프로젝트 |

| 입력 | 손글씨 이미지 | 주택·지역 정보 |

3. 오늘 새로 만들 파일 3개의 이름과 역할을 말할 수 있습니까?  
├── housing_model.py         ←  주택 가격 모델 정의 + 추론 함수
├── housing_schemas.py      ←  주택 가격 API 스키마
└── housing_api.py             ←  주택 가격 FastAPI 서버

housing_model.py: PyTorch 모델 아키텍처를 정의하고, 저장된 가중치와 전처리 파라미터를 불러와 데이터 정규화 및 실제 가격 추론(Prediction)을 수행하는 모듈입니다.

housing_schemas.py: Pydantic을 활용하여 외부에서 들어오는 데이터(요청)와 나가는 데이터(응답)의 구조를 정의하고, 범위 초과 등의 유효성 검사를 담당하는 스키마 파일입니다.

housing_api.py: FastAPI 프레임워크를 기반으로 비동기 스레드풀을 활용하여 실제 클라이언트의 요청을 받고 추론 결과를 반환하는 백엔드 서버(API) 파일입니다.
(참고: 프론트엔드 폴더에 UI 구성을 위한 app_housing.py도 함께 생성하게 됩니다.)



✅ 체크포인트  
1. 정규화에서 학습 데이터의 통계를 테스트 데이터에도 사용하는 이유는 무엇입니까?  
: (표준화) 모델은 학습 데이터의 평균과 표준편차를 기준으로 변환된 값을 보고 학습했기 때문에 테스트 데이터에 별도의 평균과 표준편차를 사용하면 학습 당시와 입력 기준이 달라집니다.  
따라서 모델이 학습할 때 기준으로 삼았던 학습 데이터의 통계(평균, 표준편차)를 그대로 적용해야만 데이터 누수(Data Leakage)를 방지하고, 모델이 배포되었을 때와 동일한 조건에서 성능을 평가할 수 있습니다.  

2. 모델 가중치 외에 함께 저장해야 하는 것은 무엇이고, 왜 필요합니까?  
: 모델 가중치(.pth)와 함께 전처리 파라미터(학습 데이터의 평균, 표준편차, 피처 이름 등)를 .json 등의 형태로 반드시 저장해야 합니다. 배포된 서버에서 사용자가 원시 데이터(Raw Data)를 입력했을 때, 이 데이터들을 모델에 넣기 전 학습 당시와 완벽하게 동일한 기준으로 정규화(스케일링)해야 정상적인 예측 결과가 나오기 때문입니다.  

3. HousingPredictor.predict()에서 피처를 self.feature_names 순서로 배열하는 이유는?  
: 모델은 입력값의 이름을 이해하는 것이 아니라, 각 값이 들어오는 위치를 기준으로 계산하기 때문입니다.  

API(FastAPI 등)를 통해 전달받는 JSON이나 딕셔너리 데이터는 클라이언트의 요청에 따라 피처의 입력 순서가 뒤섞일 수 있습니다. 머신러닝 모델(다층 퍼셉트론)은 내부적으로 특성의 '순서(인덱스)'를 기준으로 가중치를 곱하도록 고정되어 학습됩니다. 만약 순서를 맞추지 않고 들어온 대로 텐서로 변환하면, 모델이 '주택 연식'에 곱해야 할 가중치를 '중위 소득'에 곱하는 치명적인 오류가 발생하므로 이를 방지하기 위해 강제로 순서를 정렬하는 것입니다.  


✅ 체크포인트  
1. HousingRequest에서 Latitude에 ge=32, le=42 제한을 넣은 이유는?  
: 모델이 학습한 데이터가 '캘리포니아 주택 가격' 데이터여서 캘리포니아 지역의 위도 범위에 맞는 입력만 허용하기 위해서입니다. 캘리포니아주의 실제 위도는 대략 32도에서 42도 사이에 위치합니다.  
Pydantic의 유효성 검사(Validation) 기능을 사용하여 이 범위를 벗어나는 값(예: 한국의 위도나 완전히 잘못된 숫자)이 입력되면 서버 단에서 즉시 422 에러로 차단함으로써, 모델이 학습하지 않은 엉뚱한 데이터로 인해 잘못된 예측 결과가 나오는 것을 방지합니다.

2. request.model_dump()는 어떤 역할을 합니까?  
: FastAPI 엔드포인트로 들어온 요청 객체(request)는 Pydantic 모델 클래스 인스턴스입니다. model_dump() 메서드는 이 Pydantic 객체를 파이썬의 표준 딕셔너리(dict) 형태로 변환해 줍니다. 머신러닝 모델의 추론 함수(predict())가 딕셔너리 형태의 입력을 받아 피처 값을 추출하도록 설계되어 있기 때문에, 호환성을 맞추기 위해 사용됩니다. (이전 버전의 Pydantic에서는 .dict()로 사용되었습니다.)  

3. run_in_executor를 사용하지 않으면 어떤 문제가 발생할 수 있습니까?  
: FastAPI는 기본적으로 비동기 이벤트 루프(싱글 스레드)를 기반으로 동작합니다. PyTorch 모델이 추론을 수행하는 작업은 CPU 연산을 많이 요구하는 동기적인 '블로킹(Blocking)' 작업입니다. run_in_executor를 사용하지 않고 메인 스레드에서 모델 추론을 바로 실행하면, 연산이 끝날 때까지 서버 전체가 멈추게 되어 다른 클라이언트의 API 요청을 전혀 받을 수 없는 병목 현상이 발생합니다. 이를 스레드풀로 넘겨 비동기적으로 처리함으로써 서버의 동시 처리 능력을 유지할 수 있습니다.  

** 파이썬 스레드(Thread)는 하나의 프로그램 안에서 여러 개의 코드를 동시에 실행할 수 있게 해주는 작은 작업 단위


✅ 체크포인트  
1. MNIST 대시보드(Day 4)와 비교했을 때 입력 방식이 어떻게 다릅니까?  
Day 4의 MNIST 프로젝트는 '이미지' 데이터를 다루었기 때문에 사용자가 직접 숫자를 그리는 마우스 캔버스나 이미지 파일 업로드 방식이 필요했습니다. 반면, 이번 주택 가격 예측 프로젝트는 '정형 데이터(수치형 데이터)'를 다루는 회귀 모델이므로, 사용자가 8가지 특징(소득, 연식 등)에 대해 직접 숫자를 입력하거나 조절하는 폼(Form) 기반의 텍스트/숫자 입력 방식을 사용한다는 점이 다릅니다.  

정리하면:  
MNIST:  
이미지 업로드 → 이미지 인코딩 → 숫자 분류.  

주택 가격:  
숫자 항목 입력 → JSON 구성 → 가격 예측.  

2. st.number_input()에서 min_value, max_value를 설정하는 이유는?  
프론트엔드(UI) 단에서의 선제적인 유효성 검사를 위해서입니다. 백엔드(FastAPI)에도 제한이 걸려 있지만, 화면 단에서 미리 범위를 지정해 두면 사용자가 실수로 비상식적인 값(예: 마이너스 인구수, 캘리포니아를 벗어난 위도 등)을 입력하는 것을 원천 차단할 수 있습니다. 이를 통해 불필요한 API 호출을 줄이고 사용자 경험(UX)을 향상시킬 수 있습니다.  

3. request_data 딕셔너리의 키 이름이 HousingRequest 스키마의 필드 이름과 정확히 일치해야 하는 이유는?  
프론트엔드에서 request.post를 통해 보낸 JSON 데이터는 백엔드 도착 시 Pydantic 클래스인 HousingRequest를 통해 자동으로 매핑되고 검증됩니다. 이때 딕셔너리의 키 이름이 스키마에 정의된 변수명(예: MedInc, HouseAge 등)과 대소문자 하나라도 다르면, 백엔드에서는 필수 데이터가 누락된 것으로 간주하여 즉시 422 Unprocessable Entity 에러를 반환하고 추론을 거부하기 때문입니다.  




✅ Day 5 최종 체크포인트  
Q1. 전처리 파라미터(mean, std)를 모델과 함께 저장해야 하는 이유는?  
: 실제 배포된 서비스 환경에서 사용자가 새로운 데이터를 입력했을 때, 모델이 학습할 당시와 완벽하게 동일한 기준으로 정규화(스케일링)를 적용해야 하기 때문입니다. 학습 데이터의 평균과 표준편차 기준이 없으면 새로운 입력값을 모델이 해석할 수 있는 올바른 스케일로 변환할 수 없어 예측의 정확도가 완전히 무너지게 됩니다.  

Q2. HousingRequest에서 Latitude에 ge=32, le=42를 넣은 이유는?  
: 해당 모델이 '캘리포니아' 지역의 주택 데이터로만 학습되었기 때문입니다. 캘리포니아의 실제 위도 범위(약 32~42도)를 벗어나는 데이터가 서버로 들어오면 Pydantic이 미리 422 에러로 차단하게 하여, 모델이 처음 보는 엉뚱한 값으로 무리하게 예측을 시도하는 것을 선제적으로 방지합니다.  
  
Q3. Streamlit의 입력값 이름이 Pydantic 스키마의 필드 이름과 일치해야 하는 이유는?  
: Streamlit(프론트엔드)에서 데이터를 딕셔너리로 묶어 FastAPI(백엔드)로 POST 요청을 보낼 때, 백엔드의 Pydantic 클래스가 이 키(Key) 이름들을 기준으로 데이터를 자동으로 매핑하고 유효성을 검사하기 때문입니다. 이름이 하나라도 다르면 필수 데이터가 누락된 것으로 간주되어 서버가 요청을 거부합니다.  

Q4. 이 프로젝트에서 run_in_executor를 제거하면 어떤 문제가 생길 수 있습니까?  
: FastAPI는 기본적으로 싱글 스레드 기반의 비동기 이벤트 루프로 동작합니다. run_in_executor를 제거하여 무거운 CPU 연산(PyTorch 모델 추론)을 메인 스레드에서 직접 실행하게 되면, 연산이 끝날 때까지 서버 전체가 멈추게(Blocking) 되어 다른 클라이언트들의 동시 요청을 전혀 처리하지 못하는 심각한 병목 현상이 발생합니다.  

Q5. MNIST 프로젝트(Day 1~4)와 오늘 프로젝트의 가장 큰 차이는 무엇입니까?  
: 다루는 데이터의 형태와 태스크(문제 해결) 유형이 완전히 다릅니다.  
  
MNIST (Day 1~4): '비정형 데이터(이미지)'를 다루었으며, 숫자가 무엇인지 카테고리를 맞히는 분류(Classification) 문제였습니다. 따라서 그림을 그리는 캔버스 UI와 이미지 변환 로직이 필요했습니다.  
  
오늘 프로젝트 (Day 5): '정형 데이터(소득, 연식 등 8개의 수치 피처)'를 다루었으며, 연속된 값인 주택 가격을 예측하는 회귀(Regression) 문제였습니다. 따라서 텍스트/숫자 입력 폼 UI와 통계적 수치 정규화 로직이 필요했습니다.
